# Golang for DevOps — Self-Paced Bootcamp

A hands-on, self-paced curriculum to take you from "I've heard of Go" to "I can ship Go-based DevOps tooling." Free, public, and community-supported.

> **Honest expectations:** This is run in spare time. Questions in Discussions get a best-effort reply within ~a week. The strongest learners help each other.

## Who this is for

- Engineers comfortable with at least one of Python, Bash, TypeScript, or Java
- Working in (or moving toward) DevOps / Platform / SRE / Cloud roles
- People who learn by doing, not by reading

## How the bootcamp works

1. **Pick a pace.** A reasonable rhythm: 1 section per week. Faster if you have time; slower if you're juggling. There are no due dates.
2. **Read the section's `README.md`** — concepts, mental models from other languages, the DevOps angle.
3. **Walk through the numbered examples** — each is a tiny runnable program demonstrating one concept. Read the code, run it, change things.
4. **Build the mini-project** — every section ends with a small real-ish DevOps tool. Tests verify your implementation.
5. **Try the exercises** — extra prompts to deepen understanding. Each ships as failing tests; you write code until they pass.
6. **Get help when stuck.** See "How to ask for help" below.

## Curriculum

See the [roadmap table](./README.md#roadmap) in the main README.

Recommended order: top to bottom (00 → 11 → projects). Each section builds on earlier ones. You *can* skip around once you're past `00-setup` and `06-testing`, but you'll see callbacks to earlier sections.

## How to ask for help

**Use [GitHub Discussions](https://github.com/alialjaffer/golang-learning/discussions)** for:
- "I'm stuck on exercise X" — share your code (a gist or branch link) and the error/test output
- Concept questions ("why does Go do X this way?")
- Show-and-tell ("I built something on top of section 05")

**Use [GitHub Issues](https://github.com/alialjaffer/golang-learning/issues)** for:
- Bugs in the repo's code or test files
- Typos, broken links, factual errors
- Improvement suggestions

Three issue templates are provided to make this easier — pick the right one when filing.

## How to ask a good question

Save everyone (including yourself) time:

1. **Quote the section + exercise number.** e.g. "section 05-concurrency, exercise 02-broadcast"
2. **Paste the error or failing test output.** Use a code block (triple backticks).
3. **Share your code.** A [GitHub gist](https://gist.github.com/) or a branch link works. Don't paste 200 lines inline.
4. **Say what you've already tried.** "I tried X expecting Y but got Z" — this is gold for anyone helping.

## Want to help others?

If you finish a section, hang around. Answer one Discussion. Fix one typo. That's how this becomes more than my personal repo.
